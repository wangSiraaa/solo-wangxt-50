# 试模对照工作台（Mold Trial Workbench）

面向模具工程师的整改/复测追溯系统：**一项整改究竟解决了哪个模腔、在哪组工艺参数下解决的缺陷**，必须可被精确回答。

- **后端**：Spring Boot 3.3 / Java 21 / Spring Data JPA
- **前端**：Angular 18（standalone components，无 UI 框架依赖）
- **数据库**：PostgreSQL 16
- 虚构模具：**M-118 端盖注塑模（一出四 C1–C4）**，R1→R2→R3 三个版次、三轮试模

---

## 1. 容器启动

```bash
docker compose up --build
```

| 服务 | 地址 |
| --- | --- |
| 前端工作台 | http://localhost:8088 |
| 后端 API | http://localhost:8080/api |
| PostgreSQL | localhost:5432（库 `moldtrial` / 用户 `mold` / 密码 `mold`） |

首次启动时：

1. Hibernate 自动建表；
2. `SchemaInit` 通过 JDBC 安装**只追加触发器**（`retest`、`rectification_record` 禁止 UPDATE/DELETE）；
3. `SeedService` 写入虚构演示数据（幂等，重启不重复）；
4. `StartupCheckRunner` 自动执行一次一致性检查并打印到后端日志：

```bash
docker compose logs backend | grep 一致性
```

重置演示数据：

```bash
docker compose down -v && docker compose up --build
```

## 2. 数据一致性检查

```bash
# 仅业务规则检查（7 项），通过 HTTP 调用后端
./scripts/consistency-check.sh

# 额外用 psql 验证数据库触发器确实阻止 UPDATE/DELETE（需要本机有 psql）
./scripts/consistency-check.sh --db
```

也可以在前端「一致性检查」页随时手动触发。检查项：

1. 每个已关闭问题必须挂接一条 **PASS 且条件匹配** 的复测；
2. 关闭复测的版次/工艺条件**当前仍**落在问题适用窗口内；
3. 复测/整改外键完整性；
4. 最新复测为 FAIL 的问题不能是 CLOSED（失败必须回到整改）；
5. 已发布批次不存在未关闭的适用严重问题；
6. 无游离样件证据；
7. 只追加触发器在位。

## 3. 核心业务规则

- **一缺多腔、分别确认**：T1 中同一个“浇口烧焦”严重缺陷同时影响 C1/C2/C3，登记为 DEF-001/002/003，各自整改、各自复测、各自关闭。
- **关闭必须关联适用范围内的复测结果**：复测记录模具版次 + 料温/模温/注射速度/保压。只有版次与四个参数全部落在问题的适用窗口内，PASS 才可用于关闭。
- **换版次/换窗口的成功样件不能自动证明旧问题解决**：PASS 但条件越界时，系统把复测改记为 `CONDITION_MISMATCH`（条件不符），不允许关闭。
- **复测失败回到整改，但不覆盖上次失败**：复测、整改均为只追加表，数据库触发器层面禁止 UPDATE/DELETE；时间线永久保留每次失败。
- **批次发布前置条件**：全部**适用的严重问题**关闭后才可发布通过（主要问题未关闭仅提示）。跨批次延续问题按其适用版次计入对应批次；并发发布由乐观锁保护。
- **并发关闭**：问题带 `@Version` 乐观锁，两位工程师同时关闭同一问题时，先提交者成功，后提交者得到 **409**。

## 4. 虚构演示数据与建议演示路线

### 预置数据

| 批次 | 版次/参数组 | 情况 |
| --- | --- | --- |
| B-T1 | R1 / PG-A 标准窗口 | 浇口烧焦 DEF-001/002/003（严重，C1/C2/C3）、缩印 DEF-004（主要，C4） |
| B-T2 | R2 / PG-B 降温降速窗口 | R2 整改验证轮 |
| B-T3 | R3 / PG-C 高速实验窗口 | 实验性工艺窗口 |

复测时间线（只追加）：

| 复测 | 问题 | 条件 | 结果 | 说明 |
| --- | --- | --- | --- | --- |
| RT-001 | DEF-001 | R2/PG-B 范围内 | **PASS** | 已据此关闭（关闭人：质量-陈敏）——**局部解决**：同一缺陷三腔中仅 C1 关闭 |
| RT-002 | DEF-002 | R2/PG-B 范围内 | **FAIL** | 第 8 模烧焦复现，问题回到整改；失败记录保留 |
| RT-005 | DEF-002 | R2/PG-B 范围内（二次整改加深排气槽后） | **PASS** | **预置但不关闭**，供两人并发关闭演示 |
| RT-003 | DEF-003 | R3/PG-C 高速窗口 | **条件不符** | 样件合格，但版次+4 项参数全部越界，不能关闭 |
| RT-004 | DEF-004 | R3/PG-C 高速窗口 | **条件不符** | 未改模，换窗口下缩印不可见 ≠ 旧问题解决 |

样件“照片”由后端按证据类型动态生成 SVG（含模腔、缺陷位置与复测工艺标注），无需外部图片资源。

### 演示 1：局部解决 + 批次发布门槛

1. 打开「批次工作台」→ **B-T2**：可见适用严重问题未关闭数为 2（DEF-002、DEF-003），发布按钮禁用，阻断项逐条列出。
2. 进入「问题台账」：烧焦缺陷组下 C1 已关闭、C2 整改中、C3 整改中 —— 一项整改只解决了一个腔。
3. 进入 **DEF-001**：查看 RT-001 合格照片与适用窗口；B-T2 此时仍不能发布，因为另外两个腔未确认。
4. （可选）B-T3 可以发布：它适用的 R3 严重问题均不在未决状态；阻断说明里不会把 R1/R2 的旧账错误算到 R3 上。

### 演示 2：复测条件不匹配（换版次/换窗口不能证明旧问题）

1. 进入 **DEF-003（整改中，无有效 PASS）**，直接点「关闭问题」→ 收到 422：最新复测 RT-003 样件合格但条件不符。
2. 在“登记复测”区点击「快速填入：R3 高速窗口」→ 前端预判列出版次/料温/模温/速度/保压全部越界；提交后该复测被记为**条件不符**（橙色），问题依旧不能关闭。
3. 再点「快速填入：范围内条件」→ 预判通过；提交 PASS 后即可关闭。
4. **DEF-004** 展示同一逻辑：未经改模，仅在 R3 窗口下取得合格样件，不构成对 R1 旧问题的证明。

### 演示 3：失败回到整改、历史不覆盖

1. 打开 **DEF-002**：时间线中 RT-002（FAIL，红色烧焦照片）之后是 RT-005（PASS）。
2. 可继续登记一条 FAIL 复测，问题回到「整改中」，RT-002 与 RT-005 均原样保留。
3. `./scripts/consistency-check.sh --db` 可直接看到 UPDATE/DELETE 被 PostgreSQL 拒绝。

### 演示 4：两人同时关闭同一问题

1. 进入 **DEF-002**（已存在范围内 PASS 的 RT-005，满足关闭条件）。
2. 点击「**👥 模拟两人同时关闭（张工 / 李工并发提交）**」：两个请求携带相同版本号并发到达。
3. 结果：一人 `200 关闭成功`，另一人 `409 冲突 —— 已被抢先关闭`；刷新后关闭人唯一。
4. 此后再关闭会收到 422「已由 X 关闭，请勿重复关闭」。

### 演示 5：两轮试模参数/缺陷对照

- 打开「两轮对照」，默认 **B-T1（R1）→ B-T2（R2）**：
  - 参数表显示料温、模温、速度、保压窗口中点全部下调；
  - 缺陷表按 C1–C4 对齐：C1「本轮关闭 ✅」（关闭依据 RT-001）、C2/C3「仍未解决 ❌」、C4「仍未解决」。
- 切换 **B-T2 → B-T3** 可看到窗口跳变（高速化）以及“新窗口成功样件”在 DEF-003/004 上仅被记为条件不符。

## 5. 主要 API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/batches` / `/api/batches/{code}` | 批次列表/工作台详情（含发布阻断项） |
| POST | `/api/batches/{code}/release` | 发布通过（严重问题未关闭 → 422） |
| GET | `/api/issues` / `/api/issues/{code}` | 问题台账/详情（含复测、整改时间线） |
| POST | `/api/issues/{code}/rectifications` | 登记整改（可更新适用版次/窗口） |
| POST | `/api/issues/{code}/retests` | 登记复测（PASS 越界自动改记条件不符；FAIL 回整改） |
| POST | `/api/issues/{code}/close` | 关闭问题（无有效复测 422；并发 409） |
| GET | `/api/comparison?from=B-T1&to=B-T2` | 两轮参数与缺陷对照 |
| GET/POST | `/api/consistency/check` | 数据一致性检查 |
| GET | `/api/evidence/{id}/photo` | 样件 SVG 证据图 |
| GET | `/api/evidence/svg?kind=&title=&caption=&verdict=` | 动态生成证据图 |

## 6. 本地开发（可选）

```bash
cd backend && mvn spring-boot:run

cd frontend && npm install && npm start   # http://localhost:4200，已配置 CORS
```
